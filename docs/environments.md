# Environments

Lindra runs in four tiers: a throwaway stack per ticket, a preview stack per card in review, one long-lived test stack and the operator's production stack. All four use the same `compose.yaml` and the same script, `scripts/env.py`. The decision is in `docs/adr/0007-environments.md`; this file is the procedure.

## Commands

Run them from a checkout with `python3 scripts/env.py <command>`. The script needs Python 3.12, git and Docker with the compose plugin; rootless Docker is the supported setup. Every command can run twice and ends in the same state. An exit code of 0 means success, 1 means a check or an action failed, and 2 means the command cannot run as asked.

| Command | What it does |
| --- | --- |
| `up` | Builds the image, starts the stack and waits until it is healthy. It creates the env file with a generated token when none exists (a throwaway stack takes `LINDRA_PREVIEW_TOKEN` instead when it is set), and runs the seed hook when the volume has not been seeded. `--tier test` and `--tier production` pick the other tiers; `--project`, `--port` and `--bind` adjust a stack. |
| `check` | Calls `/health`, the authenticated route `/api/session` with the token, and `/api/environment`. It fails unless both backends are the stand-ins and the three cast cases are in case storage for the current cast, so a redeploy that changes the cast, or a deleted cast case, fails `check` until `reset` or `up` seeds again. It exits non-zero on any failure, including a stack that is down. With `--remote` it checks the test tier through `LINDRA_TEST_URL` and `LINDRA_TEST_TOKEN` instead of a local stack. |
| `reset` | Calls the seed hook, which loads the fictional cast and nothing else. The hook stores each cast case in case storage with its assessment and visits, replacing a stored case of the same case number. Cases the physician created under other numbers stay. A second run leaves the same state. |
| `down` | Removes the containers, the network and the volume. A throwaway stack also loses its image and env file, so a later `up` starts clean. The test tier keeps its env file so the published token stays valid, and production keeps its volume and env file; `--purge` removes those too. |
| `ensure-test` | Test tier only. Fetches `origin/main` and compares it with the commit the running stack reports. If they differ, or nothing answers, it checks out `origin/main`, runs `up --tier test` and then `check --tier test`. Otherwise it does nothing. It refuses to run in a checkout that is on a branch other than `main`, or that has uncommitted changes. |
| `install-timer` | Writes `lindra-test-env.service` and `lindra-test-env.timer` into `~/.config/systemd/user`, reloads systemd and enables and starts the timer. The timer runs `ensure-test` every 5 minutes. `--dry-run` writes the units to a temporary directory (or `--unit-dir`), prints them, runs `systemd-analyze --user verify` on them and installs nothing. |

The user running the timer needs lingering so the timer survives logout: `loginctl enable-linger lindra-test`. Ticket 03 does this when it installs the test tier.

## Files and variables

`up` writes `.lindra-env/<compose project>.env` with the token, the port, the bind address and the tier. Git ignores the directory, and the file is readable by its owner only. The token comes from `secrets.token_urlsafe(32)`, with one exception: a new throwaway env file takes the token from `LINDRA_PREVIEW_TOKEN` when that variable is set (see "Preview procedure"). Nothing in the repository holds a token, a URL of a real stack or a real name.

Nodes read two variables from their profile to reach the test tier:

| Variable | Value |
| --- | --- |
| `LINDRA_TEST_URL` | The base URL of the test tier, for example `http://<host>:8780` |
| `LINDRA_TEST_TOKEN` | The token in `.lindra-env/lindra-test.env` on the test node |

The operator puts both into the node profile when ticket 03 is done. `scripts/env.py check --remote` reads them and never prints the token.

The service reads `LINDRA_TOKEN`, `LINDRA_DATA_DIR`, `LINDRA_TIER`, `LINDRA_COMMIT`, `LINDRA_TEXT_BACKEND` and `LINDRA_SPEECH_BACKEND` (see `.env.example`). `compose.yaml` sets both backends to `fixture` and takes no value for them from the env file. The evaluation configuration reads further variables, listed under "Evaluation configuration".

## Stand-ins and the fictional cast

The throwaway, test and production stacks run two deterministic stand-ins (ADR 0003):

| Service | Stand-in | Source |
| --- | --- | --- |
| Text model | fixture model that returns the expected draft and clarification items of a cast encounter | `lindra/standins.py` |
| Speech recognition | canned transcripts, keyed to the fixture audio of the cast | `lindra/standins.py` |

Input outside the cast is refused, so a test cannot pass on invented output. In every tier `LINDRA_TEXT_BACKEND` and `LINDRA_SPEECH_BACKEND` accept only `fixture`; the self-hosted and hosted backends stop the service at start with a message that names the evaluation configuration. They start only there, see "Evaluation configuration".

The cast lives in `lindra/cast.py` and is the only dataset: three invented German cases with case numbers `FIK-2026-001` to `FIK-2026-003`, invented patient names, a treatment period, an admission assessment and at least one visit each. One visit is backdated. The second case has an assessment change accepted after a visit draft was generated: the seed hook stores that case as its timeline left it, so its assessment holds an accepted draft (accepted twice), its visit of 16.10.2026 holds an accepted draft that shows "Hintergrund seit Erstellung geändert", and its backdated visit of 14.10.2026 holds a pending proposal. The other two cases come as notes only, so a draft is generated from nothing. The third case leaves gaps and carries contradictory doses and an unclear time reference. Every encounter has notes, an expected draft and clarification items, and every case has fixture audio with a canned transcript. The audio is generated from a key (a short tone) and no audio file is committed. The seed hook refuses a cast that breaks these rules.

Real, pseudonymised or production-copied patient data never goes into a tier or into the repository, and neither do the ward's forms or the operator's documents (ADR 0006).

## Evaluation configuration

The evaluation configuration is the one place a real backend runs (ADR 0003, ADR 0007, ticket 11). It is not a tier of `scripts/env.py`: nothing in the compose files or in `env.py` selects it, and no tier defaults to it. It is `LINDRA_TIER=evaluation`, which only `scripts/evaluation.py` sets, on the host that runs the inference servers.

| Variable | Meaning |
| --- | --- |
| `LINDRA_TEXT_BACKEND` | `fixture` (default), `selfhosted` or `hosted` |
| `LINDRA_TEXT_URL`, `LINDRA_TEXT_MODEL` | the local inference server (default `http://127.0.0.1:11434`) and the model it serves; the model is required |
| `LINDRA_SPEECH_BACKEND` | `fixture` (default) or `selfhosted`; there is no hosted recogniser |
| `LINDRA_SPEECH_URL`, `LINDRA_SPEECH_PATH`, `LINDRA_SPEECH_MODEL` | the recogniser server (default `http://127.0.0.1:8080`, route `/inference`, model optional) |
| `LINDRA_HOSTED_URL`, `LINDRA_HOSTED_MODEL` | the hosted comparison's address and model, both required |
| `LINDRA_HOSTED_KEY` | the operator's own account key. Read from the process environment only, never from an env file, never printed |

The rules the service enforces:

- Outside `LINDRA_TIER=evaluation` any backend but `fixture` stops the service at start. This includes a settings object built in code, not only the environment.
- `LINDRA_TIER=evaluation` in an env file is refused. It must come from the process environment, which `scripts/evaluation.py` sets.
- In the evaluation configuration the service refuses to start when the database holds a case whose number and patient name are not those of the cast. The message names the case number and never the patient name.
- A text or speech request for a case whose number and patient name are not both the cast's, for example one created after the start or a cast number under another name, is refused before it reaches a real backend.
- The hosted address must be https unless it is a loopback address, must carry no user name or password, and a redirect from it is an error, so the key never goes to another host.
- The hosted comparison needs the three hosted variables. `scripts/evaluation.py` also needs `--approved`, the operator's statement that the run and its spend are approved.
- There is no fallback. A failing real backend gives a failed generation or transcription, never the fixture's answer.

`docs/evaluation/real-backends.md` has the commands, the measuring tool and the record. `/api/environment` reports `evaluation: true` and the backends in use. `scripts/env.py check` still fails on anything but the stand-ins.

## Throwaway procedure

Use this on the node that runs the ticket. It never touches the test tier or production.

1. `python3 scripts/env.py up --project lindra-<ticket>` builds and starts the stack and seeds the cast. The output names the URL and the env file.
2. `python3 scripts/env.py check --project lindra-<ticket>` must exit 0.
3. `python3 scripts/env.py reset --project lindra-<ticket>` runs the seed hook again. A second run reports the same digest.
4. `python3 scripts/env.py down --project lindra-<ticket>` removes everything. `check` now exits non-zero.

## Preview procedure

The operator checks some changes before merge, for example dictation on an iPad. For that the Workboard runs a preview stack of the card's branch while the card is in review. It is a throwaway stack with a fixed project name, a port from a reserved range and a token the operator knows. The script does not check the name or the port range; the Workboard keeps to them.

| Item | Value |
| --- | --- |
| User | `factory` |
| Node | the node that built the card |
| Port | one port from 48600 to 48619, bound to `127.0.0.1` |
| Compose project | `lindra-pv-<card>` |
| Published at | the node's `tailscale serve`, which forwards an HTTPS port to the stack's port |
| Login token | the value of `LINDRA_PREVIEW_TOKEN` |
| Data rule | the fictional cast and nothing else; the stand-ins, as in every tier |
| Teardown | when the card leaves review |

1. From a fresh `git worktree add --detach` of the card's branch, with `LINDRA_PREVIEW_TOKEN` in the environment, run `python3 scripts/env.py up --project lindra-pv-<card> --port <port>`. A fresh checkout has no `.lindra-env` yet; `up` creates it. The stack listens on `127.0.0.1:<port>` and nowhere else, so only `tailscale serve` on the node makes it reachable.
2. `python3 scripts/env.py check --project lindra-pv-<card>` must exit 0.
3. The node publishes the port with `tailscale serve`. The Workboard shows the resulting HTTPS link on the card's Preview tab.
4. The operator opens the link and logs in with the token held in `LINDRA_PREVIEW_TOKEN`.
5. When the card leaves review, the Workboard removes the `tailscale serve` entry and runs `python3 scripts/env.py down --project lindra-pv-<card>`. That removes the containers, the volume, the image and the env file. `check` now exits non-zero.

`up` reads `LINDRA_PREVIEW_TOKEN` only when it creates the env file of a throwaway stack. An existing env file keeps its token, and `--tier test` and `--tier production` never read the variable. Without it, `up` generates a token as before, and nobody can read that token from outside the node, so a preview needs the variable. The token may hold letters, digits and `.`, `_`, `~` and `-`; any other character makes `up` exit with code 2 before it starts anything. `up`, `check` and `down` never print the token.

## Test procedure

The test tier was installed by ticket 03 on 2026-11-10, as node `lindra-test` on Linux 790 after the operator's suitability check.

| Item | Value |
| --- | --- |
| Host | Linux 790, `minisforum790.tail974337.ts.net` |
| URL | `http://minisforum790.tail974337.ts.net:8780` (the value of `LINDRA_TEST_URL`) |
| Port | 8780 |
| Compose project | `lindra-test` |
| Installed | 2026-11-10 |

1. In the dedicated checkout on `main`, run `scripts/env.py up --tier test`, then `check --tier test`, then `install-timer`.
2. From then on the timer runs `ensure-test` every 5 minutes. A new commit on `origin/main` is deployed without anyone touching the stack. Read the result with `journalctl --user -u lindra-test-env.service` on the test node.
3. From another node, set `LINDRA_TEST_URL` and `LINDRA_TEST_TOKEN` and run `scripts/env.py check --remote`. The `commit` line of the output names the deployed commit.
4. `scripts/env.py reset --tier test` on the test node seeds the fictional cast again.

Nobody edits the test checkout by hand; `ensure-test` stops when it finds uncommitted changes.

## Production runbook

The operator follows this as `frogger`. Production is never deployed by a ticket or an agent.

Before the first run, name the host and record it in "The production host is open" below, with the note that it is the evaluation host and not a cleared clinical host. Docker must run rootless for `frogger`.

1. Clone the repository: `git clone https://github.com/tomorrowflow/lindra.git`, then work in the checkout.
2. Choose the commit. It must be a `main` commit that the test tier runs and that passes `check`. With `LINDRA_TEST_URL` and `LINDRA_TEST_TOKEN` in the profile of `frogger`, run `scripts/env.py check --remote` and read the commit in its last `ok` line. Confirm that the continuous integration run for that commit is green.
3. Check it out: `git fetch origin main`, then `git checkout --detach <commit>`.
4. Deploy: `python3 scripts/env.py up --tier production --port <port> --bind <address>`. The first run generates the production token in `.lindra-env/lindra-prod.env`. Keep that file with the operator and never commit it. Later runs reuse the token, port and address. `check` and `reset` reach the stack on that address; a wildcard address (`0.0.0.0` or `::`) is reached through loopback.
5. Verify: `python3 scripts/env.py check --tier production` must exit 0. A passing check says the stack works. It does not authorise real patient data.
6. To update, repeat steps 2 to 5 with a newer commit. To roll back, check out the earlier commit and run step 4 again. The volume stays.
7. To stop the stack, run `scripts/env.py down --tier production`. Add `--purge` to remove the volume and the env file as well.

`reset --tier production` seeds the fictional cast and nothing else. No real, pseudonymised or production-copied patient data may be loaded into production without the separate approval of ADR 0006, and a host that meets the legal and organisational check (ADR 0007).

## The production host is open

The host for real clinical use is an open decision. It depends on the legal and organisational check in `docs/research/2026-11-04-legal-frame-patient-data-and-llms.md`: a cloud host would have to meet §393 SGB V, an in-hospital or physician-side box would not, and the hospital's own approval is needed either way. Until the decision exists, ticket 04 installs the evaluation configuration on a host the operator names, and a passing `check` there is not an authorisation for real data (ADR 0006, ADR 0007).

| Item | Value |
| --- | --- |
| Production host | open |
| Evaluation host | `zotac1070.tail974337.ts.net`, named by the operator on 2026-11-10 (ticket 04). It is the evaluation host, not a cleared clinical host, while ADR 0007's decision is open. |
| Real patient data | not allowed |

`zotac1070.tail974337.ts.net` is not connected to the OpenClaw environment, so no factory node, ticket or agent reaches it. The operator installs and checks the stack there as `frogger`.
